# coc-connector

Consolidated messaging connectors behind one `MessagingConnector` contract. No CoC/forge dependencies.

## Layout

- `src/core/` — provider-neutral contract: `MessagingConnector`, `InboundMessage`, `ConnectorStatus`, `SendOptions`, `MessagingTarget`, `MessagingConnectorOptions`. Exported from the package root (`@plusplusoneplusplus/coc-connector`).
- `src/teams/` — `TeamsBot`, transports, auth, clients. MCP owners can select Graph channel reads independently of discovery/operations; standalone Graph timestamp polling stays opt-in. Exported from `@plusplusoneplusplus/coc-connector/teams`.
- `src/teams/operations.ts` — typed send/reply/Like contract and fixed per-owner routing.
- `TeamsBot` selects a poll/admission routine at construction; scheduling, references and errors are shared. Hybrid `mode: mcp, channelReadBackend: graph` uses the ID/thread scanner, not standalone Graph timestamp admission.
- `src/teams/graph/` — Graph client, outbound operations, standalone polling transport and identity-pinned `GraphChannelReader` page provider.
- `src/teams/ic3/`, `src/teams/mcp/` — backend implementations: IC3 credentials, self/verified existing 1:1 sends, Likes, and operations; MCP client, operations, and polling transport. Public exports stay in `src/teams/index.ts`.
- `src/whatsapp/` — `WhatsAppBot` over Baileys (lazy `import()`). Exported from `@plusplusoneplusplus/coc-connector/whatsapp`.
- `teams/`, `whatsapp/` — proxy `package.json` redirects (`main`/`types` → `../dist/...`). They exist so consumers built with `moduleResolution: node10` (which ignores the `exports` map) can resolve the subpaths. Keep them in sync with the `exports` map.

## Conventions

- **Subpath exports, not a flat barrel.** Teams and WhatsApp both export a type named `BotStatus` with different unions; subpaths keep every exported name unchanged and collision-free.
- **`getStatus()` is normalized** to `ConnectorStatus`. Each bot keeps its native `_status` for internal logic and maps on the way out. WhatsApp maps `qr-pending → pairing`, `creating-group → busy`; use `WhatsAppBot.getNativeStatus()` when the native value is needed (e.g. REST status output). `createGroup()` reports `creating-group` and then the restored status through `onStatusChange` (unless the connection changed mid-call), so observers never stay on `creating-group`.
- **`SendOptions.mentions` are keyed by `id`.** `TeamsBot.send` maps `id → aadId` before calling its transport.
- **MCP polling is adaptive.** `TeamsBot` polls every 12 seconds while active and every 30 seconds after a minute without new inbound messages. A whole-poll HTTP 429 honors `Retry-After` or uses jittered exponential backoff capped at five minutes; successful polling clears the cooldown. Poll errors reach `onError` and clear on recovery; an unrecoverable token-refresh failure stops polling until reconnect. Optional `onPoll` and `onInbound` observers receive only safe outcome/skip enums, and observer exceptions cannot interrupt polling or routing.
- **Trouter inbound defaults off** (`enableTrouter`). `trouter.ts` uses Node 24 WebSocket, separately acquired IC3-audience credentials pinned to the reader's tenant/object identity, fixed registrar/endpoint, heartbeat/ACKs, lease renewal and cancellable jittered reconnect. Real activity `sourceThreadId` takes precedence over synthetic `48:` streams; only the selected conversation wakes reads. Unknown source is ignored. `notification-scheduler.ts` coalesces a bounded (64 roots) single-flight mailbox, reconciles on loss/disconnect/overflow, syncs at startup and schedules fallback 60 seconds after completion. Reader HTTP429 windows also gate wakes; outbound sends never restore short polling. Notifications never carry admission authority or message content.
- **Notification health is independent of reader connectivity.** `TeamsBot.getNotificationStatus()` and standalone `TrouterClient.getStatus()` expose state plus sanitized typed error; `trouterOptions.onError` observes safe categories without provider bodies. Session generations reject stale socket/registrar callbacks. Public `TrouterClient` supports credential-injected, handler-free protocol smoke via `start()`, `getStatus()`, `stop()`; each instance is disposed permanently on stop. `trouterAccount` extracts the identity pin, not message authority. No configured target means no wakes.
- **Notification reads are best-effort, not durable delta.** The hybrid/MCP channel scanner pages toward the last admitted root head (`commitNotificationRead`); bound/discovered-root wakes read only hinted histories, completing reply pagination without root scans. Unknown/missing roots, startup, fallback and gaps reconcile known threads without fabricated bindings. Targeted reads retain backfill/watermarks. Failed reads retry after two seconds with hints and HTTP429 cooldown; fallback remains 60 seconds. Reads have a five-minute deadline and caps (100 cursors/5,000 replies per thread/10,000 messages per scan), fail rather than commit incomplete reads/admission, and cancel on stop. Hybrid Graph uses full reply pages in ordinary polls too. Standalone Graph timestamp polling is best-effort. Thread reads retain `pollChannelReplies`; DM autodiscovery/probes are disabled with Trouter.
- **MCP HTTP sessions complete initialization and recover on expiry.** `McpClient` sends `notifications/initialized` and carries the session id and version on later requests. Reads recover an expired session once on 404; outbound operations disable session replay. HTTP errors expose status and `Retry-After` without authorization headers.
- **Channel thread polling is opt-in.** `pollChannelReplies` gates both hybrid Graph replies and MCP replies (which also require advertised `ListChannelMessageReplies`). MCP ordinary polls rotate five tracked roots; hybrid Graph reconciles known roots with complete reply pagination. `onChannelRootDiscovered` persists identities before reply admission. Dated historical repo/topic controls carry `historicalSelectionReplay` for silent reconstruction, distinct from `initializationReplay` (Like suppression). Pre-start/undated questions are suppressed. Hybrid Graph establishes an independent reply cutoff on re-enable while roots stay live. Durable known/own-ID callbacks survive reconnect; admission failures retry. Default MCP/DM polling retains last-message behavior. Backfill requires trustworthy timestamps; retention/skew remain best-effort limits.
- **Channel reaction admission is upstream of routing.** Inbound messages retain Teams application authorship so CoC can skip bot-authored posts. Graph channel polling is live opt-in via `pollGraphChannel`; it establishes a new watermark on enable, reads up to 50 recent roots per poll, and filters timestamps locally because Graph channel listing does not support `$filter`. Graph DMs remain send-only. MCP admits unseen bound replies during its initial poll with `initializationReplay` so CoC can route them without reacting to history. Connector deduplication excludes own, empty, and unchanged posts before reaction admission; DMs do not react.
- **Outbound identity:** `TeamsDestination` distinguishes self/chat/channel; inbound/outbound references retain backend, connection, and thread. `TeamsBot.sendMessage`/`replyToMessage`/`reactToMessage` retain deduplication. Routes/credentials are instance-scoped; callers own workspace bindings. Only discovered self-chat IDs identify a chat as self, never arbitrary IDs or the first `ListChats` result.
- **MCP reader / Graph writer:** explicit `operationRoutes.channelSend/channelReply: graph` plus `graphOutboundOptions` registers `GraphOperations` alongside MCP/IC3. `GraphCredentialStore` owns cancellable acquisition, validates Graph audience/expiry/delegated `ChannelMessage.Send` or existing `Group.ReadWrite.All`, and pins tenant/object identity to the MCP reader before connection and refreshed writes. Initialization captures its client/lifetime; stale completions cannot replace restarted operations. Channel IDs and reply roots stay unchanged; stop cancels credentials/writes and routing never falls back.
- **Hybrid Graph reader:** `channelReadBackend: graph` plus optional `graphReadOptions.acquireToken` selects Graph beta root/reply pages independently of write routes and MCP tool advertisement. Beta is a preview API subject to change; outbound Graph sends/replies and standalone Graph clients retain stable v1.0. Normal CoC always selects the hybrid reader; standalone MCP defaults to MCP reads. Read credentials validate delegated `ChannelMessage.Read.All` (least privilege) or existing `Group.Read.All`/`Group.ReadWrite.All`, separately from write consent, pinned to the same MCP account. Every page validates the beta collection-scoped next link; 401 refreshes once, 429 honors Retry-After, errors are sanitized/actionable, and failed reads never fall back. Inbound references record Graph; the normal Like adapter retains exact MCP/IC3 channel/message IDs and its IC3 route.
- **Graph consent:** successful `/me` does not prove channel-write access. Both channel posts and replies accept delegated `ChannelMessage.Send` (least privilege, recommended for new clients) or an existing `Group.ReadWrite.All` compatibility grant. Never request the broader grant for this feature. Azure CLI sign-in/backend selection does not grant consent. Connector consumers may supply `graphOutboundOptions.acquireToken`; normal CoC uses Azure CLI tokens without a custom-client auth setting.
- **IC3 ordinary sends use explicit routing:** select `operationRoutes.chatSend: ic3` and call `sendMessage({kind: 'chat', chatId, recipientId, connectionId: bot.getConnectionId()}, body)`. Ordinary sends require fresh MCP `GetChat`/`ListChatMembers` reads proving the exact existing `oneOnOne` ID and complete, distinct current-account/intended-recipient membership. Missing metadata/tool access rejects explicitly without Graph chat consent or ID translation. Standalone IC3 owners inject `verifyChat`, account and connection pins. Raw `send(target, text)` is not the ordinary IC3 entry point; chat creation, groups, channels, mentions and replies are unsupported by the IC3 sender. Self identity stays explicit; chat references never impersonate self. IC3 self sends are always supported via `operationRoutes.selfSend: ic3` and map to `48:notes`, without replies/mentions. Default connector self routing uses MCP; IC3 self routing skips discovery writes and polls only an explicit reader chat target.
- **IC3 connection safety:** credentials and explicit optional region (`amer`, `emea`, `apac`) are snapshotted; send/Like share credential handling. An unset region rejects IC3 writes with typed `configuration`/`not-attempted` before credentials/network. No endpoint override, region default, or cross-region replay. Hybrid MCP pins tenant/object identity and fails closed on missing/mismatched credentials. Account/region/routes require reconnect; ordinary sends require a current connection ID, rotated when an IC3-chat-routed MCP transport reinitializes. Verification, credentials and write share the ten-second cancellation deadline. IC3 send IDs are not inbound polling targets.
- **Likes/deadlines:** Graph channel `setReaction` uses Unicode thumbs-up (HTTP 204). MCP explicitly maps channel references to IC3's exact message `emotions` property on undocumented chatsvc; Graph references are not translated. Writes share a ten-second deadline including credentials; cancellation/disposal prevents late dispatch.
- **Errors/replay:** `TeamsOperationError` carries backend/code and `not-attempted`/`rejected`/`unknown`. Routers never retry/fail over; MCP/Graph may refresh once on typed HTTP 401, IC3 never replays. Missing IDs, malformed success, and uncertain delivery are unknown; send failures do not imply polling disconnect. MCP alone doubles backslashes; text/HTML is explicit and unsupported options reject before dispatch. `isError`/`Error:` results produce sanitized `TeamsMcpSendRejectedError`, never provider bodies.
- Baileys + qrcode-terminal are `optionalDependencies` — installed but only loaded by WhatsApp use.
- The WhatsApp connection factory receives an abort signal from `WhatsAppBot`; stop cancels pending reconnect timers and prevents late callbacks from reviving the bot.
- WhatsApp inbound messages expose the chat JID, optional group participant JID, and paired-account `fromMe` flag; `senderJid` remains the chat JID for container consumers. `WhatsAppBot.react()` sends a Baileys reaction with a five-second rejection timeout.
- `shared/commands.ts` is the one Teams/WhatsApp command grammar (`parseMessagingCommand` + generated help). Mode prefixes `/ask`, `/autopilot`, `/ralph`, and `/sentinel` require a slash and a message body; plain text leaves mode undefined (callers keep the chat's mode). Explicit `[chatid]` targeting composes with every mode prefix.
- `whatsapp/message-utils.ts` contains CoC-independent outbound formatting, lossless WhatsApp text chunking, and the container bridge's `[global]` prefix parser. The container bridge uses the helpers without changing its short-message formatting or routing.

## Build / test

- `npm run build -w packages/coc-connector` (tsc → `dist/{index,core,teams,whatsapp}`). Must build before `coc`/`coccontainer` compile or run tests that resolve via `dist`.
- `npm run test:run -w packages/coc-connector` (moved Teams/WhatsApp tests + `test/core` conformance).
